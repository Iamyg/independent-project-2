Abstract 
This report implements and evaluates the R2T (Race -to-the-Top) differential privacy 
query algorithm. R2T uses smart truncation and a τ-value racing mechanism to 
maximize query accuracy while protecting individual privacy. Experiments were 
conducted on the TPC-H dataset (SF=0.1, about 100MB), testing two types of aggregate 
queries—COUNT and SUM —each run 10 times. The results show that the average 
relative error is 1.41% for COUNT queries and 1.82% for SUM queries, with a standard 
deviation of errors below 0.7%, confirming the effectiveness of the algorithm. 
Keywords: Differential Privacy; R2T; TPC-H; Truncation Mechanism 
1. Background of the project  
1.1 Overview of Differential Privacy 
Differential Privacy, or DP for short, is the go -to standard for protecting data privacy. 
It's already being used by big names like Apple, Google, and Microsoft. The main idea 
is pretty simple: if you have two databases that are almost the same except for one 
person's data, the results you get from running a query on them should look so similar 
that you can't really tell which database is which.

1.2 The challenges of the Relational Database 
Applying differential privacy in relational databases faces a special challenge: the 
foreign key constraints. Take TPC-H as an example: 
 

PAGE 2
CUSTOMER(c_custkey)ORDERS(o_custkey)LINEITEM(l_orderkey) 
 
A customer may own hundreds of even thousands of orders. Adding or deleting a 
customer can cause the query result to change dramatically, making the global 
sensitivity practically infinite. The traditional Laplace mechanism would have to add 
noise proportional to that sensitivity, which would completely destroy the usability of 
the result. 
 
1.3 The introduction of the R2T algorithm 
R2T (Race-to-the-Top) was proposed by HKUST and Duke University at SIGMOD 
2022, specifically designed to handle differential privacy queries with foreign key 
constraints. Its core features are: 
 
Feature Description 
Instance optimality Error is close to the theoretical lower bound 
Adaptive truncation No need to know the optimal threshold in 
advance 
Logarithmic dependence Error scales only with log(GS_Q)

2.2 Key innovations of R2T 
1. Race mechanism: Let multiple τ values compete and automatically select the 
optimal one 
2. Theoretical guarantee: Error reaches O(log(GS_Q) · loglog(GS_Q) · DS_Q / ε) 
3. Generality: Supports arbitrary SPJA queries(including self-joins)

4.3 Simple truncation implementation 
For the Q3 query without self -joins, simple truncation is used (proved optimal in the 
paper): 
def compute_Q_tau(psi_values, c_j_sets, tau): 
    result = 0 
    for c_j in c_j_sets: 
        total = sum(psi_values[k] for k in c_j) 
        result += min(total, tau)  
    return result

6.4 Key finding 
Finding 1: The error for full-table queries is much lower than for queries with WHERE 
clauses. 
Query Type With WHERE (year 1995) Full Table

Reason: Full-table queries have a large cardinality, so the DS_Q / |Q(I)| ratio is small. 
 
Finding 2: Good error stability 
1.COUNT standard deviation is only 0.49% 
2.SUM standard deviation is only 0.67% 
3.Results across 10 trials are highly consistent 
 
Finding 3: SUM error is slightly higher than COUNT error 
Possible reason: The distribution of order amounts is uneven — a small number of high-
value orders account for a large share, leading to a higher DS_Q / result ratio.

7. Future direction 
7.1 Support for GROUP BY queries 
Currently, R2T only supports single -value aggregation. Approaches for handling 
GROUP BY: 
Approach 1 (Split): Run R2T independently for each group, dividing the privacy budget 
by the number of groups 
Approach 2 (Extended LP): Introduce independent variables for each group 
 
7.2 Handling self-join queries and Testing on larger-scale data 
Self-join queries (such as triangle counting in social networks) require LP truncation 
rather than simple truncation, and the current framework can be directly extended. 
Using SF=1 (1GB) or even SF=10 (10GB) data
